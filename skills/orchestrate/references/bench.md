# Benchmark history

`orch bench` stores finished gate runs, exact subjects, immutable answer keys,
and deterministic comparisons. It does not run models or execute suite arms.
Use the full wrapper path `~/.agents/skills/orchestrate/scripts/orch` in place
of `orch` below.

## Private store

Resolution is `ORCH_BENCH_DIR`, then
`${XDG_DATA_HOME:-~/.local/share}/orchestrate/bench`. The store is machine-local
on purpose: it contains private spec and item text, prompts and repository
paths. Directories are 0700; files are 0600. Archives have no redaction.
Never put the store in a source repository. Nothing is automatically pruned.

```
store.json                         schema_version 2
README.md                          created if absent; an existing guide is preserved
objects/spec/<hash16>.md            byte-exact spec text, maximum 2 MB
objects/spec/<hash16>.json          SHA256, packages, history, variant, itemset
objects/itemset/<id16>.json         canonical items and their origin
objects/blob/<sha256>               prompts, console, notes, small dirty patches
subjects/<subject-id>.json          repo, commit evidence, dirty state, spec
<suite>/suite.toml                  initial comparison scope, subject default, arms
<suite>/reports/suite-proposals/<sha>.toml  later definitions; never auto-applied
<suite>/keys/key-N.json             normalized key, subject, itemset, provenance
<suite>/keys/key-N.original.json    immutable source JSON
<suite>/keys/key-N.md               provenance and prompt text
<suite>/runs/<id>/run.json          schema 2 record, subject and object references
<suite>/runs/<id>/snapshot/         gate, items, checklist, report, subject (old runs also carry dossiers)
<suite>/runs/<id>/shadow.jsonl      stored shadow rows
<suite>/runs/<id>/score-key-N.json   preserved old unversioned rescore, if present
<suite>/runs/<id>/scores/<sha>.json  new versioned score envelope, content addressed
<suite>/runs/<id>/migrations/<sha>.json  proposed run reconstruction, never an overlay
migrations/store-<sha>.json         proposed schema 2 store metadata, if schema 1
<suite>/reports/history-<sha>.md    immutable content-addressed history
<suite>/reports/index.md            derived listing, retains historical entries
_inbox/                            untouched original provenance
```

The spec ID is the gate's 16-hex `specHash`. `spec_sha256` is a separate full
SHA256, never a second spec ID. Package content hashes join versions by package
ID. An item set is identified by the SHA256 prefix of canonical item JSON;
parser order and legacy key order are retained. Empty item sets are valid.
Shared content retains the first registration's metadata; later records do not
rewrite its origin, timestamp or spec provenance.

A subject binds repository identity, commit evidence, dirty fingerprint and
spec version. Its ID is `s-<hash16>-<commit7|nocommit>[-dirty]-<facts6>`; only
tracked modifications add `-dirty`. The suffix is the first six hex characters
of SHA256 over repository identity, dirty state/path lists/diff hash, commit
basis and commit evidence. Path lists are sorted; absent and empty lists agree.
Timestamps, descriptions and derived patch-storage fields do not affect the ID.
Identical evidence gives the same ID; different evidence can coexist. A residual
short-hash collision still fails the immutable-subject check rather than overwriting data.

Objects, subjects, keys, runs, snapshots, prompts and original scores are immutable.
`bench migrate` and `bench key rescore` never rewrite `run.json`, an existing key,
`score-key-N.json` or store metadata. A subject correction is a proposal with a new
subject object; the original subject and its binding remain unchanged. New keys
still use the next `key-N`, optionally with a `base_key`. An arm name does not overwrite its original suite definition;
each run retains the resolved config it actually used. Recording initializes a
new `suite.toml` once. Later definition/default additions become immutable
`reports/suite-proposals/<sha256>.toml` files instead of rewriting the suite. Reports
never apply these proposals. The shared copy helper also refuses to replace
different existing bytes. Automatic record/key/archive operations and explicit
`bench readme` create a guide only when `README.md` is absent; they preserve an
existing guide, including one generated by an older binary.

## Capture and import

```
orch bench record /path/to/finished-gate --suite reuse --label original --arm code
orch bench import /path/to/experiment --suite reuse --label short --arm code-short
orch gate spec.md --only group:api --experiment short --bench-suite reuse
```

Automatic experiment recording uses explicit `--bench-suite`, then `bench_suite`
in the user config. The default is no automatic recording. Repo `bench_suite`
is ignored; `orch doctor` reports that once. For `bench record`, explicit
`--suite` takes precedence over the same user setting. Import requires both
`--suite` and `--label`.

Names use 1-64 ASCII letters, digits, `.`, `_`, or `-`, start with a letter or
digit, and cannot contain `..`. `objects`, `subjects`, and `_inbox` are not suite
names. Path containment checks resolve symlinks, including the nearest existing
parent of a new path. Record components are validated again when loaded.
Informational raw and spec paths are never write or delete destinations.

Every non-dry gate run writes `subject.json` at start, sharing the checkout
guard fingerprint. This records the actual commit, spec state and working-tree
state before model work. A capture error becomes a note, not a gate failure.
Recording copies the artifacts, so `pruneGate` cannot erase stored history.
Sessions and repository code are not copied by default. Exploration summaries
are captured while sessions are available. `--with-sessions` includes sessions.
Pass prompts are content-addressed blobs up to 8 MB per run; beyond that their
hashes are retained without storing the prompt bodies. Tracked dirty patches
up to 256 KB are blobs; larger patches retain their fingerprint and size.
Untracked files are listed, never copied.

Historical imports try a stored subject, registered spec text, the repository's
current text, and then byte-exact blobs from all git branches. `--repo PATH`
overrides repository discovery; orchestrate run roots are resolved through their
`.repo` marker, not assumed to be checkouts. `--spec-text FILE` must hash to the
gate's spec ID. Missing text is an explicit unknown and an informational verify
finding. Run item sets omit the spec-object reference when text is unknown;
the run and subject still retain the known spec hash. A report-only directory
must be named by its 16-hex spec ID:

```
orch bench import /gate/0123456789abcdef --suite history --label old --kind report-only
```

New gate captures record the v2 `state`, not the old `status` derivation.
Report-only runs preserve `report.md`, but have null findings. A v2 review-state
line supplies `state`; an old Status line supplies only `historical_status`.
The read-only shim in `tool/gate_legacy_read.go` also retains old gate.json and
bench archive labels. Historical labels never imply a v2 state or plan approval.
Original records remain unchanged. Their `created_at` is the import date, not
an invented execution date. No counts are extracted from prose.

Historical commits and dirty state are never taken from the checkout today or
inferred from dates. To assert a historical commit:

```
orch bench import /gate/HASH --suite reuse --label old --repo /repo \
  --commit abcdef1234567 --commit-basis note \
  --commit-evidence 'Exact sentence or source that records this commit'
```

A reachable repository must contain that commit. `--commit-basis` accepts only
`user` or `note`; it requires evidence. `--dirty-from FILE` accepts historical
`git status --porcelain=v1` output. A note about unspecified uncommitted changes
is not a porcelain status file and is not silently converted into one.

`--console FILE` stores exact console output. `--console-start FILE` additionally
requires an explicit RFC3339 or `HH:MM:SS` start in that file and an explicit end
timestamp as the console's last line. Wall clock is separate from summed pass
seconds. Missing costs, turns, runner, author and build provenance stay unknown.
Cost is never computed from tokens or a current price list.

## Specs and keys

```
orch bench spec add --from-git /repo docs/spec.md --all-versions
orch bench spec add builds.md --variant-of HASH --label builds-7 --notes NOTES.md
orch bench key add reuse key.json --note 'Recorded review provenance' \
  --from-run original --blind unknown --prompt prompt.md
orch bench key add reuse key-v2.json --note 'Independent review' \
  --subject SUBJECT --author 'Recorded reviewer' --blind true \
  --items blind-items.json --base-key key-1 --prompt group1.md --prompt group2.md
```

Old reference arrays and new `class`/`target` keys remain readable. Current
quality scoring uses behavior identities; historical location-overlap scores
remain visible only as `legacy` heuristics. Originals and prompt blobs are preserved. Blind items accept `text` or
legacy `item`. IDs must match. Old reference item text must also match; a new
key's `seeks` description remains in its original JSON while blind items supply
the canonical deliverable text. Repeated `--prompt`
flags preserve separate exact blobs. Omitted author and blindness are `unknown`.
`--git-status FILE` can bind a key to historical dirty-state evidence, subject to
the subject fingerprint and immutable-subject checks above. `--subject` and `--from-run` are
exclusive. Without either, the suite default is used only when its runs do not
span several subjects.

## Read, score and compare

```
orch bench list --suite reuse
orch bench show reuse/original
orch bench compare reuse original short --baseline original --key 2 --md
orch bench compare reuse original short --total
orch bench key rescore reuse short --key 2
orch bench report reuse --runs original,short --since 2026-01-01 --key 2 --save
orch bench report reuse --json
```

The newest key is the default and is always identified. Read-only comparisons
recompute scores in memory from snapshots. They do not write runs, keys or score
artifacts. Key coverage is restricted to packages in the compared groups.

`bench key rescore` is the explicit score-write command. It first makes a private,
isolated copy of the store and runs verification there. A validation error stops
before any source-store write. It never rewrites a key or adds `key_subjects` to
an old run. On success it writes only a new immutable `scores/<sha256>.json`
artifact beside that run. The same inputs and scorer produce the same file, not
another timestamped score. Source inputs are checked again before publication.

Each envelope records `scorer_schema_version` (`bench-score/v1`),
`profile_version` (`behavior-identity/v1`), a deterministic `population_id`, and
`mapping_id` (SHA256 of the exact adjacent `mapping.json`, or `unknown`). Its
`inputs` list records the relative path, object ID, SHA256 and recorded/unknown
state of every archived scoring input and referenced subject, spec, itemset and
prompt object. Hash-only prompts retain their IDs with unknown stored bytes.
The embedded `score` retains per-class precision/recall denominators, exclusions,
answer coverage counts and visibility unknowns. `metric_warnings` explains missing
measurements and unavailable metrics. Scorer versioning is not current gate
approval, and it cannot supply a missing historical subject or measurement.

Reports label preserved unversioned scores as **old recorded (legacy)** beside
**new scores** recomputed with the named scorer/profile. Neither report nor
rescore silently applies a migration proposal. New score artifacts preserve an
auditable calculation, not a claim that the run is reproducible. `--save` uses a
content-addressed report name and adds its index entry once. Repeating the same
report does not create another report or index entry. Existing report files are
never rewritten; only the derived index may change, without dropping old entries.

A key behavior keeps its own ID even when another behavior has the same target.
`candidate` is one acceptable evidence target; optional `candidates` is an array
of alternatives, not extra behaviors. These optional fields can be supplied in
the immutable original key JSON. Scoring also reads optional `revision`, or
recovers it from the key's stored itemset. Evidence alternatives use existing
`path:line[-line]` or `path#Symbol` pointers. Identity matches exact stable ID and
revision first. Legacy IDs without revisions join directly only within the same
known itemset. There is no approximate text join and no 80% match threshold.
Any missing, ambiguous or stale mapping makes dependent quality metrics
`unavailable`; the full key population and identity issues remain in the report.

Cross-version mappings are explicit, hand-written `mapping.json` next to the key
files, for example `<suite>/keys/mapping.json`. The file can contain bindings for
several keys and run itemsets:

```json
{
  "schema_version": 1,
  "mappings": [{
    "key": "key-2",
    "from_itemset": "KEY_ITEMSET_ID",
    "to_itemset": "RUN_ITEMSET_ID",
    "items": [{
      "key_id": "api#save",
      "key_revision": "KEY_REVISION",
      "item_id": "api#persist",
      "item_revision": "RUN_REVISION",
      "candidates": ["src/store.py:10-30", "src/store.ts:20-40"]
    }]
  }]
}
```

Both population IDs must match stored itemsets. Each source and target identity
must exist exactly once and revisions must match. Empty revisions are permitted
only when the archived identity has no revision, with both itemsets still bound.
Duplicate population bindings, split/merge mappings, unknown IDs, stale revisions
and invalid target pointers cannot authorize quality claims. Optional mapping
`candidates` overrides the key's targets when source locations moved. Omit it to
retain the key's alternatives. An unmatched population binding is not applied.
Mappings are never proposed or written by compare/report. A non-mutating
`bench key --map-preview` is not part of this implementation.

`gate compare --reference FILE` uses the same rules and an adjacent mapping file.
Its mapping `key` is the reference file's basename, `from_itemset` is SHA256 of
its exact bytes, and `to_itemset` is the canonical itemset ID for that arm's
`items.json`. Reference rows can include `id`, `revision` and `candidates`.
Legacy text references stay visible as legacy location evidence, but do not
silently join current behaviors.

Current accuracy scores explicit `reuse`, `extend`, `new` and `unclear`
judgments. A generic reuse finding is not an explicit duplicate judgment. Current
answers must validate against the recorded review item/revision, evidence packet
and explicit support assessment. An unverified or invalid candidate cannot be a
correct positive. Historical findings, shadow rows without support assessments,
and locator-only verification remain inspectable but are not supported answers.
Historical range-overlap scores are labeled `legacy` and never rank workflows.

Each quality section states its denominator and exclusions:

- Answer coverage is answers present / all keyed behaviors, including unclear.
  Valid and supported coverage use the same denominator. Missing, invalid and
  unsupported answers are counted separately, never dropped from that population.
- Conditional accuracy is correct supported answers / supported mapped answers.
  Reuse/extend correctness also requires an acceptable target. If identity is not
  established, conditional accuracy is unavailable, not zero.
- Precision is supported correct predictions / supported predictions of that
  class within the mapped key. Non-key predictions are excluded. Recall is
  supported correct predictions / all keyed behaviors of that class, including
  behaviors without a supported answer. F1 uses those two behavior denominators.
- Retrieval, author hints and rendered targets are separate counts / all key
  behaviors with targets. Only a valid rendered source manifest spanning the
  entire acceptable target establishes body visibility. A checklist candidate,
  same-file author hint or overlapping signature does not. Missing delivery
  instrumentation is unknown, not unseen. No checklist means retrieval unknown.

Unknown metrics print `not recorded`, not zero. Historical total native reads are
recovered only from an actual total-read counter. Missing range or shell
breakdowns remain unknown, including in JSON output. Partial cost totals are
marked incomplete. A smaller reuse count is not by itself proof of better quality.

Same-subject comparisons are direct. Other commits warn about location drift.
Other versions of the same spec path join package content hashes; registered
variants are allowed and identified. Other repos or spec paths require
`--cross-subject`. Group rows use the intersection. `--total` refuses different
group sets; `--total=all` explicitly opts into all recorded passes with a warning.
These switches permit display, not a ranking. Comparative change claims and
quality/cost Pareto rankings require identical known subjects, itemsets and full
pass/package coverage. Quality rankings also require identical mapped key
populations, complete supported-answer coverage and complete known costs. A run
with no compatible eligible peer is explicitly not ranked. Thus one-group and
eleven-pass runs can be inspected together without producing an unlabeled winner.

Reports include Subjects, tested-on lines, configuration and subject differences,
runner/lane subtotals, quality/cost, shadow confusion, caveats and reproduction.
Multiple recorded changes are confounded. Unknown commits are not reproducible;
asserted commits are not presented as git-verified checkout commands. Stored
comparisons work without the original checkout or raw gate directory.

## Verify, migrate and transfer

```
orch bench verify --suite reuse
orch bench migrate --suite reuse
orch bench migrate --suite reuse --run original --commit abcdef1234567 \
  --commit-basis user --commit-evidence 'Explicit historical assertion'
orch bench export reuse --out reuse.tar.gz
ORCH_BENCH_DIR=/tmp/bench-restore orch bench import-archive reuse.tar.gz
orch bench readme
```

Verify checks content hashes, references, snapshot gate hashes, immutable key
originals and run/subject spec agreement. Missing raw paths, missing repositories,
unknown text and asserted commits are information, not errors. Errors exit 1.
Migration writes a `bench-migration/v1` proposal under each run's `migrations/`,
with the original run SHA256 and `proposed_run`. Unknown v1 fields survive in that
proposal. Its `basis` marks reconstructed registration/history timestamps as a
deterministic `created_at` anchor, not a correction or evaluation date.
Subject correction keeps console/prompt evidence and proposed history,
but does not alter the original binding. Newly reconstructed snapshot data stays
inside the proposal, not in the archived snapshot. Reconstructed subjects/objects
are added immutably. Schema 1 store metadata gets a separate proposal under the
root `migrations/`; `store.json` and `README.md` are not rewritten. Commands that
require an actual store-schema upgrade can still refuse a schema 1 store; migration
does not silently authorize that upgrade. Missing subjects remain informational
legacy unknowns in verification and reports. Migration is idempotent, executes
reconstruction in an isolated copy, and stops if it needs to replace an existing
object. It never imports runs or automatically rewrites keys.
Archives include only the suite and
its original run/key-referenced subjects and objects, never `_inbox` or another
suite. Proposal files travel with the suite, but the archive reference traversal
does not follow proposed bindings. Keep a full private store backup to preserve
objects registered only by a migration proposal. Import
rejects traversal, links, duplicate members, conflicting files and archives over
512 MB or 100000 entries. Import into a fresh store is the simplest restore path.

Out of scope: executing arms (`bench run`), a cross-system usage ledger, source
code snapshots, price-table cost estimates, line remapping and export redaction.
