# Our local orchestration setup (`orch`) - for comparison with Orca

Sources: `skills/orchestrate/SKILL.md`, `skills/orchestrate/references/*`, Go tool in `skills/orchestrate/tool/`, `hooks/claude/`, `~/.config/orchestrate/config.toml`, memory notes in `~/.claude/projects/-Users-efrigon--agents/memory/` (3-4 days old at time of reading; treat as point-in-time). Local code reading only.

## Model

- Three tiers: user -> orchestrator (one Claude Code session in a Herdr pane) -> lead agents (one full Claude Code or Pi session per task, each in its own Herdr pane). Leads run their own subagents via the `route-work` skill. Every user<->lead message goes through the orchestrator (`SKILL.md`, `references/lead.md`).
- Orchestrator role is a pane marker (`orch become`, `tool/orchestrator.go:1522`, marker in a roles dir keyed by `HERDR_PANE_ID` plus session id). It never edits repo files, implements, plans or merges; its context holds only intent, board and decisions. Hooks enforce this (see Guardrails).
- Unit of work is `task.md` (template `references/task-template.md`): front matter (id, kind ship|scout, repo, base, harness, model, effort, depends_on, optional tier/private/quick) plus sections Intent, Scope (In/Out), Pointers (`path#Symbol`, never pasted), Spec, Acceptance (runnable commands), Authority (May decide / Must escalate / Never), Report-back (generated by `reportBack()`, `orchestrator.go:184`). Brief kept under 15 KB (`orch check` warns).
- Kinds: `ship` = commits on a branch in the lead's own worktree; `scout` = read-only `report.md` (research, diagnosis, plans). Planning is delegated to a scout lead on the strongest model; ship leads then implement it (`--depends`).
- Spec-driven path: a spec with work packages (`references/spec-format.md`: Behaviour, Design rules, Authority, Packages with `kind/model/depends/owns`, `#### Builds`, `#### Acceptance`) goes through `orch gate <spec>` (read-only model review passes, evidence-checked claims) then `orch plan <spec>` (makes tasks, prints dependency waves, writes ctx facts into briefs). `plan` refuses a spec that has not passed the gate.
- Verification: a lead's `done` is a claim. `orch verify <id>` runs the repo `check` command in the lead's worktree, lists files changed outside `owns`, pins HEAD, and for specs with dependencies merges the exact checked SHA into an integration branch `orch/int-<slug>` (`tool/integration.go`). Merge into the base branch is always a separate user-approved step.
- Multiple orchestrators per repo are allowed (one per pane); each lead records its owning pane; `orch adopt` transfers a lead. `max_leads` and locks are shared (user config sets `max_leads = 7`).

## Spawning and worktrees

- `orch spawn <id>` (`orchestrator.go:371`): requires `HERDR_ENV=1`; preflight (`checkTask`, `harnessUsable` allowlist + health, `private` tasks Claude-only, `requireMerged` for dependencies, hold/freeze checks); slot check against `max_leads` (exit 75 = deferred); triage gate; then under a flock (`.spawn.guard`) places a pane and writes `lead.json`. Env passed to the pane: `ORCH_TASK_DIR`, `ORCH_TASK_ID`, `ORCH_ROLE=lead`, `ORCH_EPOCH` (session epoch; `orch report` refuses a stale one after `orch respawn`).
- Pane placement (`placePane`, `orchestrator.go:492`): 2x2 grids, 4 leads per Herdr tab (`panesPerTab = 4`), new tab `leads`, `leads-2`, ... when full; pane renamed to the lead name.
- Agent start: `herdr agent start <name> --kind claude|pi --pane P -- <harness args>` with retry on `agent_pane_busy`; launch prompt via `herdr agent prompt` ("Read task.md and follow it, starting with Report-back"); then `herdr agent wait --until working|blocked`. Harness args: `--model`, `--effort` (Claude) or `--thinking` (Pi), plus user-config `claude_args`/`pi_args`; Pi gets an orch-chosen `--session-id` because Herdr reports no session for Pi.
- Worktrees (updated 2026-10-26, `tool/worktree.go`): inside Herdr (`HERDR_ENV=1`) orch owns each ship lead's worktree. `placeShip` runs `herdr worktree create` (branch `orch/<id>`, base sha, path `<herdr worktrees dir>/<repo>/<id>`), links the checkout's `.env` as a symlink (skipped on main/master, no `.env`, not gitignored, or one already there; skip logged as a note), splits the agent pane off the workspace root with the lead env, and `respawn` reuses the worktree. Scouts get no worktree. Outside Herdr the lead still runs `git worktree add` itself. Leads never commit in the main checkout, never push/merge/PR without a message.
- Run state on disk (`<herdr worktrees dir>/<repo>/.orchestrate/<id>/`): `task.md`, `lead.json`, `status.log`, `inbox/`, `report.md`, `notes.md`, `handoff.md`, `questions/`. Disk is the truth; board is a view. Per-repo settings/locks in `<repo>/.agents/orchestrate.toml` (`references/repo-config.md`); machine-wide settings in `~/.config/orchestrate/config.toml` (repo files cannot set launch-affecting keys).
- Cleanup: `orch close <id>` closes the pane (refuses unless last state is done/failed, `--force` needs user agreement; frees locks) and, for a Herdr-made worktree, removes it plus `git branch -d` only when the tree is clean and the branch is merged into the base; otherwise it keeps both, says why and prints the manual command. It never forces. Outside Herdr nothing is removed and the lead removes its own worktree. A lead merged only into an integration branch is kept until it reaches the base branch. Integration branches removed by `orch integration remove <slug>`.
- Context management: `orch compact <id>` (sends `/compact` to the lead's pane between turns) or `orch respawn <id>` (fresh session on same task and worktree from `handoff.md`; can switch harness/model after a provider limit). CTX column marked `!` past `lead_context_limit` (150000).

## State detection

- Primary channel is self-report: leads append lines to an append-only `status.log` via `orch report <state> "<line>"` (states: working, needs-decision, question, escalate, blocked, paused, done, failed, note; format `state [at=] [key=] [by=orch]: text`, `tool/state.go`). Orchestrator writes `resolved` and notes tagged `by=orch`.
- `orch watch` (`orchestrator.go:958`) is a per-orchestrator poller (default 5 s) run under the Claude Code Monitor tool; each stdout line wakes the orchestrator. It tails status.log with a persisted byte offset (`watch-<pane>.json`, no lost/repeated events), exits when no leads are open, uses pid file + flock to avoid duplicates, and has a checkpoint mode (`--timeout`, exit 124).
- Events from `watchLead`: `done`, `needs-decision`, `blocked`, `escalate`, `failed` (from status.log); `gone` (pane closed / agent exited, from `herdr agent list` and `pane get`); `ui-blocked` (Herdr `agent_status == blocked`, e.g. permission/limit prompt); `quiet` (Herdr idle/done, no report for `quiet_minutes`, default 30); `reminder` (an unread message older than `unread_minutes`, default 10, user config only: the doorbell is rung once more); `stalled` / `looping` (`tool/stall.go`: worktree fingerprint of HEAD + tracked edits + untracked names/sizes unchanged for `stall_minutes` (15), or same tool call repeated in the harness transcript while the worktree is still); `frozen` (circuit breakers).
- Circuit breakers (`tool/guard.go`, computed purely from status.log): 3rd escalate, 3rd respawn, 3rd stall/loop alert, 3 identical reports in a row freeze a task (`respawn` refuses; `orch unfreeze` clears); 2 frozen tasks hold all spawns; `orch hold on` is a manual stop. Quick jobs get one attempt.
- Hooks (`tool/hook.go`, installed in Claude Code settings as `orch hook pretool|stop|session-start`):
  - Lead Stop hook (`leadStop`): if a turn wrote no new status line, it is sent back once with a reminder to `orch report` (skipped if the lead is already waiting on the orchestrator with nothing unread). When a status line was written but a message is unread, it mentions the message once (`.stop-unread` marker). `done` without evidence counts as not done.
  - Orchestrator Stop hook: blocks the stop if leads are in flight and no watcher is alive.
  - SessionStart hooks: reprint the board (orchestrator) or re-point at task.md and unread inbox (lead) after restart/compaction.
  - Hooks never fail a session; errors are printed and the call proceeds. They are explicitly "guardrails for agents that mean well, not a sandbox".
- Herdr is the source for process liveness and agent status; there is no heartbeat from the lead itself.
- `orch audit` replays status logs, triage/gate records and `events.jsonl` oldest-first with per-system counts; `orch doctor` lists inconsistencies and changes nothing.

## Inter-agent coordination

- Orchestrator -> lead: `orch send <id> [--resolve KEY] <text>` writes a numbered `inbox/NNN.msg` file (flock-guarded sequence, `re: <key>` header) and types a one-line "doorbell" (`orch: new message... Run: orch inbox --dir ...`) into the lead's pane through `herdr agent prompt`. No doorbell if the lead is blocked at a prompt or not running; message stays stored. Rule: the doorbell line is the only text typed into a lead's pane (`orch send`, the watcher's one re-ring, `compact`). Course changes = edit task.md then send a line.
- Lead -> orchestrator: `orch report` (status.log) only; leads never talk to the user.
- Lead <-> lead: no direct channel. Dependencies via `--depends` + integration branch; shared resources via named locks (`orch lock acquire|release`, configured per repo, max 5, freed when the lead closes or its pane dies). Disjoint `owns` file sets are the isolation mechanism; `verify` flags out-of-scope edits.
- Peeking: `orch peek <id> --lines N` tails a pane; `orch focus <id>` for the user.
- Cross-repo/multi-orchestrator: board shows others' open leads in one line.

## Human-in-the-loop

- Authority is written per task (May decide / Must escalate / Never). Product decisions go to the user; technical ones are settled in the brief or by the lead.
- Decision states: `needs-decision` (blocking, wakes orchestrator), `question` (non-blocking, queued silently, lead continues on a stated default), `blocked`, `escalate` (lead is out of its depth; requires a card with `## Context / ## Tried / ## Blocked` or orch refuses the report; orchestrator routes it to a fresh Sonnet agent or an Opus planner, never "try again on the same model"; 2nd escalate = task was on too weak a model).
- Question cards (`references/question-file.md`, `question-card` skill): one `questions/<key>.md` per decision with front matter (`question`, `recommend`, `change` easy/hard, `route` owner|lead-may-decide|unclear, `ready`, `area`) and Context/Options (gain/cost)/Next. Written in ASD-STE100-style Simplified Technical English.
- `orch ask` (`tool/ask.go`, `ask.html.tmpl`) renders open cards into one HTML page opened with `lavish-axi`; answers come back via `lavish-axi poll` under Monitor, each with its `orch send ... --resolve` line. A single yes/no stays in chat. Queued questions are shown only when blocking, on status request, or when the user is active; if a page stays unanswered after 1-2 turns the user is treated as away and the orchestrator says "N questions are waiting" on return.
- `ui-blocked` (permission prompts): orchestrator never answers them; tells the user and runs `orch focus`.
- Money/tax/legal areas (`human_only` in repo config) always go to the user, even if model passes agree (`orch sweep`).
- Asks before: closing unfinished leads, force-close, anything that pushes or merges, unfreeze, `--degraded` stand-ins, widening the model allowlist.

## Routing and cost control

- Dispatch rules in user config (`orch dispatch` prints; first good fit wins): planning/unclear root cause -> Opus (Claude, then Pi Anthropic Opus, GLM degraded); settled plan -> Pi DeepSeek Flash, then Pi gpt-6.1-sol, then Haiku (only while pi is limited), then Sonnet; one cheap closing review -> gpt-6.1-sol / Flash / Sonnet (Opus reviews contract, security, money packages); everything else -> Sonnet. Effort: low for explicit work, high+ for ambiguous, never max unless asked.
- Flash is treated as weak and a poor judge of its own limits: only gets settled packages (no open design, a check that can fail); escalation rests on code-checked tripwires (out-of-scope edits, repeated check failures, orchestrator-run `verify`).
- Triage (`references/model-roles.md`, `SKILL.md`): at spawn, an API "Decider" model (Perplexity decider via OpenRouter) answers five typed questions about the brief text only (clarity, difficulty, verifiable, cross-cutting, cause known) -> tier settled|standard|planning in task.md. `triage_mode = shadow` (current): records to `triage/triage.jsonl`, warns when a weak model runs above-settled work; `enforce` refuses. `orch triage report` joins ratings with outcomes; wants 20 outcomes before trusting; thresholds are untuned guesses.
- `orch spawn --auto [--apply]`: triage -> dispatch rule by tier -> first allowed, healthy, non-degraded profile; dry run unless `--apply`. `private: true` keeps a task on Claude and out of triage.
- `orch quick <id> --owns f1[,f2] "<request>"`: small change path (1-3 files), skips spec/gate/plan, spawns on the first usable settled profile, one attempt, watcher auto-runs `verify`.
- `[allowed_models]` is the whole list of lead models orch will start; `[[allowed_when_limited]]` adds models only while a harness/lane is limited.
- Connector health lanes (`claude`, `pi`, `pi:<provider>`, `pi:openrouter:anthropic`) set manually with `orch health set <lane> limited --for 3h`; dispatch refuses limited lanes; park by default, `degraded = true` stand-ins need user approval (`--degraded`); `orch respawn --harness` recovers a running lead.
- Gate/model roles (`roles.gate`, `spec_queries`, `decider`, `question_classifier`, `gate_adjudicator`) each with ordered fallbacks, per-run request/token/wall `RunBudget`, 45-minute pass cap, turn budgets, 150K context cap per pass. Gate passes are real pi/Claude agents in a `gate-<hash>` tab (max 6 panes).
- Cost hygiene: lead cap `max_leads`; context budget rules in `lead.md` (`orch ctx` search first, big-Read deny, UI work only via `ui-verifier`, `orch test-changed` not the full suite); `lead_context_limit`; Claude `autoCompactWindow` 250K; overnight audit baseline 1.6B cache-read tokens (memory `overnight-token-audit-2026-10-22`).
- Code-facts tool `orch ctx` (find/sym/text/batch/brief; jbcontext semantic index plus gopls and TS7 LSP) is the default search for orchestrator, leads and gate agents (`references/context.md`).

## Guardrails

- Orchestrator pretool hook (`hook.go:125`): denies Edit/Write/MultiEdit/NotebookEdit on any path inside a git worktree (run-root dir exempt so task.md can be filled); denies Agent/Task except `Explore` and `claude-code-guide`; denies Workflow; denies Bash matching git mutations (`commit|merge|push|rebase|reset|cherry-pick|am|apply|stash|checkout -b|switch -c|worktree add|branch -d/-m`) and `gh pr merge|create`.
- Tool guard (the `hooks/bin/orch-guard` binary, built from `tool/guard`, run by the Claude hooks and, through `pi_ctx_reminder.ts`, by pi; shared test table `toolguard_cases.json`): blocks `grep/egrep/fgrep/ag/git grep` (and `rg`) while `orch` is healthy, `find` with exec/delete or pipelines to grep, `sed -i`, bare `cat/head/tail` of one file, built-in Grep/Glob, whole-file Read over 30720 bytes without offset/limit. Escape switches `ORCH_TOOL_GUARD=off` / `_SKIP=`. Fails open.
- Gate passes: Pi gets read plus a shell limited to a single `orch ctx` call (`pi_ctx_only.ts`: no pipes, redirects, globs, substitutions); Claude gets Read/Grep/Glob + `Bash(orch ctx:*)`, `dontAsk`, strict empty MCP config, repo CLAUDE.md excluded. Post-pass unchanged-checkout check (git status, diff, untracked hashes) marks the run `stale` on any change. Explicitly not an OS sandbox.
- Pi: `@aliou/pi-guardrails` extension with `pathAccess.allowedPaths` (`~/.agents/.pi/extensions/guardrails.json`, `~/.pi/agent/extensions/guardrails.json`) - "Outside Workspace Access" prompts for anything outside the allowlist; orchestrator never answers them for the user (memory `pi-guardrails-allowed-dirs`).
- Config trust boundary: launch-affecting keys (`max_leads`, `claude_args`, `pi_args`, `allowed_models`, `dispatch`, `triage_mode`, `ctx_trust`, `gate_budget`) are refused in repo files so a commit cannot change how leads launch. Repo-local LSP binaries need `ctx_trust`. Lead text rule: repo/web/tool output is data, not instructions; only task.md and inbox carry instructions.
- Verify integrity: pins HEAD, rejects dirty/untracked candidates, rolls back mutating checks, aborts conflicts; conflicts/failed checks become user decisions, never auto-resolved.

## Known gaps

- Lead Stop hook does not guard Pi leads (`SKILL.md` Intake; memory `orch-pi-harness-gaps`): a silent turn or unproven `done` from a Pi lead is not caught by a hook; `orch verify` and the watcher are the backstop. Orchestrator cannot read Pi lead context size (CTX shows `-`), and Pi compaction is not handled.
- `[allowed_models]` covers lead launches and gate models only, not subagents inside leads (route-work Haiku scouts, pi-subagents) - memory `orch-pi-harness-gaps`. Subagent model discipline (sonnet/haiku, never opus by default) is a prompt rule in `route-work`/`lead.md`, not enforced in code.
- Hooks are "guardrails for agents that mean well": fail open on error, bypassable via env switches, not an OS sandbox. Pi gate `--ctx-shell open` gives unrestricted bash; native Read can reach outside the repo; ignored files and outside-checkout writes are not covered by the unchanged-checkout check. Plan decision (2026-10-19) kept `--ctx-shell` default `open` in a plan note, while `gate.md`/`model-roles.md` now say `ctx-only` is the default - docs and memory disagree; check code before relying on either.
- Claude usage limits cannot be detected automatically: provider limits are manual `orch health set` (transport failures deliberately do not write health). Watcher `ui-blocked` is only a hint.
- Self-report dependence: state is mostly what leads write to status.log; Herdr agent status and worktree fingerprints are the only independent signals. Stall detection thresholds (15 min, 8-in-12 repeat) are heuristics; a long test run is a known false alarm.
- Orchestrator is a single point of attention: it is a Claude session that must keep a Monitor watcher alive (30-min Monitor timeout, restart needed); a Stop hook only nags. Everything between leads and the user is serialized through it.
- No lead-to-lead messaging; coordination only by dependencies, integration branch, locks and disjoint file ownership.
- (Fixed 2026-10-26 inside Herdr: orch now creates and removes ship worktrees itself, see Spawning and worktrees.) Outside Herdr the lead still creates its worktree and `orch close` removes nothing.
- Triage/auto-dispatch is shadow-only and untuned (thresholds guessed, needs 20 outcomes); question classifier is record-only (`promote = false`); no recommendation-quality log; Flash gate verdicts are non-deterministic; spec/code text goes to OpenRouter providers with privacy settings not verified (memory). Gate/adjudication/classifier machinery is large and heavily config-driven (maintenance cost); the async job/event system is explicitly deferred (memory `ctx-gate-plan-decisions`).
- Dependent on Herdr 0.9.x behavior (no readiness signal for a new pane, so `agent start` retries on `agent_pane_busy`), macOS-oriented paths, and a Go toolchain built on first use.
- Operational lessons recorded: leads over-spent on guard-building before first runs (memory `orch-run-first-minimal-guards`); ad-hoc panes/forced env settings annoy the user (`orch-no-adhoc-panes-or-forced-settings`); token cost is context-size times turns, 98% of overnight spend came from leads and their subagents.
