# Orca automates plumbing; ours governs the work

Orca (stablyai/orca) and our `orch` solve different problems, so the useful comparison is by layer, not by winner. Orca is a polished desktop app whose default product is **worktree isolation with the human as coordinator**; since v1.3.24 it also ships an opt-in, still "Experimental" coordinator/worker layer driven by an `orca` CLI ([release v1.3.24](https://github.com/stablyai/orca/releases/tag/v1.3.24), [orchestration docs](https://www.onorca.dev/docs/cli/orchestration)). Ours is the reverse: an LLM orchestrator that holds the user's intent, writes contracts (`task.md`), spawns leads, verifies their claims and gates merges. Orca is clearly better at the mechanical layers: owning the worktree lifecycle, detecting agent state from several independent signals, surfacing it to a human (dashboard, notifications, phone), and supporting about 35 agents instead of two. Ours is clearly better at the governance layers: written authority per task, spec gating, independent verification before anything merges, circuit breakers, cost routing, and a config trust boundary. The best moves are to copy Orca's plumbing (worktree ownership, hook-based state signals, automatic limit detection) and to avoid its coordination features (pub/sub, nested workers, lead-to-lead mail), which are its least reliable parts. Confidence is high on Orca's worktree and status mechanics (read in code at a pinned commit), moderate on its orchestration (docs plus issues, internals unread), and limited on our side (local code reading and 3-4 day old memory notes, nothing re-run).

## Orca owns the worktree; our leads improvise it

Orca drives plain `git worktree add` from its main process, serialized, with a sanitized name, a branch prefix, a base-ref fetch (falling back to the local ref offline), and a collision loop that checks existing branches, an existing GitHub PR on the branch, the path on disk and pending background removals ([worktree-remote.ts](https://github.com/stablyai/orca/blob/main/src/main/ipc/worktree-remote.ts)). It then carries env across: linked shared directories, plus a `.worktreeinclude` file of literal gitignored paths copied under a 2 GiB budget ([worktree-include-file.ts](https://github.com/stablyai/orca/blob/main/src/main/git/worktree-include-file.ts)). An `orca.yaml` setup script runs in a visible "Setup" terminal, and with `wait-for-setup` the agent only starts after it finishes ([orca-yaml docs](https://www.onorca.dev/docs/model/orca-yaml)). Removal is a deliberate sequence: clean-check unless forced, an archive hook, a PTY sweep, `git worktree remove`, then safe `git branch -d`; an unmerged branch survives and the UI asks for review ([worktree-branch-removal.ts](https://github.com/stablyai/orca/blob/main/src/main/git/worktree-branch-removal.ts)). Agents run in a separate `node-pty` daemon, so they survive app quit, update and crash ([session-restore docs](https://www.onorca.dev/docs/model/session-restore)).

Ours splits this differently. `orch spawn` does preflight, slot and triage checks and places a pane, but it does not create the worktree: the lead runs `git worktree add` itself as instructed in the Report-back section, and removal is the lead's job or a manual `orch become --off`, `git worktree remove`, `orch become` sequence because the orchestrator's hook blocks git mutations (our_setup.md). `orch close` only closes the pane. This is our weakest mechanical spot. It makes worktree hygiene depend on a model following instructions, it leaves stale worktrees, and it forces a workaround dance on the user's most expensive session. The fix is cheap in principle because the `orch` binary already performs git mutations (it merges verified SHAs into `orch/int-<slug>` in `tool/integration.go`); the hook only constrains the orchestrator's agent tool calls, not its own subprocesses. That reading of the hook is my inference from the notes, not something re-tested.

Orca's trade-off is also instructive: its design pays for rich lifecycle code (retired-name registry, pending-removal table, WSL and SSH variants) that exists because races happened, and it writes `push.autoSetupRemote` into shared repo config as a side effect (inferred from [worktree-add.ts](https://github.com/stablyai/orca/blob/main/src/main/git/worktree-add.ts)). We need a small version: create, collision-check, set up, remove safely. We do not need the cross-platform and remote surface.

## Orca fuses five status signals; we trust self-report plus two checks

Orca's primary channel is managed hooks installed into each agent's own config. For Claude Code that covers SessionStart, Stop, StopFailure, PermissionRequest, PreToolUse and PostToolUse, SubagentStart/Stop and more; a shell script POSTs each event to a loopback HTTP server guarded by a per-start token, and spools to disk if Orca is down ([claude-managed-hook-events.ts](https://github.com/stablyai/orca/blob/44d2fcb637f7736f66a9d3e7fee26516bf31daa8/src/main/claude/claude-managed-hook-events.ts), [hook-script.ts](https://github.com/stablyai/orca/blob/44d2fcb637f7736f66a9d3e7fee26516bf31daa8/src/main/claude/hook-script.ts)). Behind it sit an OSC 7501 terminal protocol, window-title glyph parsing, a JSON screen-rules engine whose rules are downloaded from a GitHub release every 4 hours, and process-presence probes; precedence is "hooks win" ([agent-hooks README](https://github.com/stablyai/orca/blob/44d2fcb637f7736f66a9d3e7fee26516bf31daa8/src/main/agent-hooks/README.md)). Orca also installs a Claude statusLine entry that it uses for rate-limit data, which it then shows as account usage. Open issues show the cost: lost events leave status stale, a lost `SubagentStop` pins a lead at "working" for the whole session, bodies over about 1 MB are dropped, and each synchronous hook runs about 9 process execs per event, with a reporter measuring p50 166 ms ([#21327](https://github.com/stablyai/orca/issues/21327), [#15791](https://github.com/stablyai/orca/issues/15791), [#33451](https://github.com/stablyai/orca/issues/33451)). Hooks written into `~/.claude/settings.json` also collided with user config dirs ([#24873](https://github.com/stablyai/orca/issues/24873)). My read is that most of Orca's detection code is repair logic for unreliable signals.

Ours is simpler and more honest about authority: leads append to `status.log` via `orch report`, `orch watch` polls it, and independent evidence comes only from Herdr (`gone`, `ui-blocked`, `quiet`) and a worktree fingerprint for `stalled`/`looping`. The Claude lead Stop hook sends back a silent turn once, and `done` without evidence counts as not done (our_setup.md). That is a strength, because completion is a verified claim rather than a hook event, and Orca's own docs adopt a similar principle ("Safe failure: preserve work and authority and report the state as unknown", [orchestration skill](https://github.com/stablyai/orca/blob/main/skill-guides/orchestration.md)). Two gaps are real. First, **Claude usage limits cannot be detected automatically** in ours, so `orch health set` is manual; Orca's statusLine approach shows the data is reachable, though I have not verified that our Claude version exposes the same fields. Second, the stall heuristic has a known false alarm on long test runs, which a per-tool-call activity timestamp from our existing `orch hook pretool` would remove. Orca's lesson is to keep any such signal as a cheap addition with Herdr and the fingerprint as the fallback, not to build a reconciliation engine, and to keep the hook fast.

## Coordination, human input and merging: Orca is richer, ours is safer

Orca's experimental layer has Runs, dependency-aware Tasks, Dispatches, typed messages (`worker_done`, `escalation`, `question`, `heartbeat`), FIFO per-run delivery with explicit ack and replay, group addresses like `@idle` and `@claude`, nested workers and decision gates ([orchestration docs](https://www.onorca.dev/docs/cli/orchestration)). The coordinator is an ordinary agent following a shipped skill, and the Run "never schedules or places workers". Reliability is the weak point: delivery to non-chat workers is a PTY paste, so readiness is heuristic per agent, and open issues include a dispatch that reports success while the prompt stays unsubmitted ([#34010](https://github.com/stablyai/orca/issues/34010)), a lost `worker_done` that is not recovered, child worktrees never removed, and users asking for orchestration that "just works" ([#15190](https://github.com/stablyai/orca/issues/15190), [#14303](https://github.com/stablyai/orca/issues/14303)). Third-party reviews that call orchestration "future work" are outdated ([AgentConn](https://agentconn.com/blog/orca-ade-agent-fleet-parallel-coding-agents-2026/)), but nobody has hands-on benchmarked it, and I found no usage numbers.

Our channel shape is the same (file plus doorbell typed into the pane) with a sturdier core: `orch send` writes a numbered `inbox/NNN.msg` first and only then rings the doorbell, and skips the doorbell if the lead is blocked at a prompt, so the message is never lost, only late. Orca similarly refuses text-plus-Enter while a permission menu is showing and has delivery receipts (`input_accepted`, `turn_started`) ([orca-cli skill](https://github.com/stablyai/orca/blob/44d2fcb637f7736f66a9d3e7fee26516bf31daa8/skill-guides/orca-cli.md)); we lack the "turn actually started" confirmation. We have no lead-to-lead channel by design: coordination is `--depends`, an integration branch, named locks and disjoint `owns` file sets, with `orch verify` flagging out-of-scope edits. I recommend keeping that. Orca's own open roadmap (pub/sub #25578, agent profiles, planner/coder/reviewer templates #29938) suggests its model needs more machinery to be dependable, while our model avoids shared-state problems by construction.

For human-in-the-loop, ours is more disciplined and Orca's is more convenient. Ours has per-task Authority (May decide, Must escalate, Never), blocking versus queued questions, escalation cards that refuse to post without Context, Tried and Blocked, a Lavish page for batched answers, and `human_only` areas for money and legal (our_setup.md). Orca has a kanban dashboard (Needs You, Working, Done, Idle), a threaded feed, OS notifications with different timing for "needs input" and "done", a Dock badge and a mobile companion with E2EE pairing and push ([notifications docs](https://www.onorca.dev/docs/notifications), [mobile docs](https://www.onorca.dev/docs/mobile)). Its push payload carries up to 180 characters of the agent's last message or tool input through the push gateway and APNs/FCM; that is an inference from the schema, and the repo promises no logging, but it is a privacy cost we should not copy ([push-contract](https://github.com/stablyai/orca/blob/44d2fcb637f7736f66a9d3e7fee26516bf31daa8/cloud/packages/push-contract/src/send-messages.ts)). Users already ask Orca to separate "needs input" pushes from "done" pushes ([#33192](https://github.com/stablyai/orca/issues/33192)), which is exactly the one signal worth pushing for us.

On merging, Orca does almost nothing automatic. Its recipe is to race N worktrees on one prompt, review the diffs, annotate lines and send the notes back to an agent, open a PR from the winner and delete the losers ([parallel-agents recipe](https://www.onorca.dev/docs/recipes/parallel-agents), [annotate-ai-diff](https://www.onorca.dev/docs/review/annotate-ai-diff)). It adds "Resolve with AI" for paused merges and a safe branch-preserve rule, but no merge queue, integrator role or semantic conflict detection, and its own merge UI still has gaps ([#28022](https://github.com/stablyai/orca/issues/28022)). Ours is stronger: `orch verify` runs the repo check in the lead's worktree, pins HEAD, lists out-of-scope files, merges the exact checked SHA into an integration branch, aborts on conflict and turns conflicts into user decisions; merging into the base branch always needs approval. The claim that Orca "suits independent tasks only" is a reviewer inference from vendors with a commercial motive (Traycer, Crewly) rather than a product limit, but given the unproven orchestration layer it is a fair description of the safe use today.

## Side-by-side by area

| Area | Orca (verified unless noted) | Ours (from local notes) | Verdict |
|---|---|---|---|
| Worktree create | App creates it: sanitize, prefix, collision loop, base fetch, env carry-over, setup script | Lead runs `git worktree add` from instructions; `orch` does not | Orca better |
| Worktree remove | Clean check, archive hook, PTY sweep, safe `branch -d`, preserved-branch review | Lead or manual `become --off` dance; `orch close` leaves worktree | Orca better |
| Agent spawning | Catalog of about 35 agents, per-agent prompt injection, PTY in a survivable daemon | 2 harnesses (Claude, Pi) via Herdr, model allowlist, preflight, slot and triage gates | Orca broader; ours more controlled |
| Status detection | Hooks, OSC 7501, title parsing, screen rules, process probes; many stale-state bugs | Self-report plus Herdr status, fingerprint stall detection, circuit breakers | Orca richer; ours simpler and verified-claim based |
| Limit detection | Statusline rate-limit data, account usage shown | Manual `orch health set` | Orca better |
| CLI | Very broad `orca` CLI with `--json`, skills printed from the binary; no MCP server | Focused `orch` (spawn, watch, verify, gate, plan, ask, ctx) | Different scope; ours is tighter for its job |
| Coordination | Run, Task, Dispatch, ack mailbox, groups, nested workers; experimental and buggy | File inbox plus doorbell, depends, locks, disjoint `owns`; no lead-to-lead | Orca more features; ours more reliable by design |
| Human in the loop | Dashboard, notifications, phone push, decision gates | Authority per task, question cards, Lavish page, `human_only` areas | Orca better UX; ours better governance |
| Merging | Manual: race, review, annotate, PR; AI conflict help | `verify` plus pinned-SHA integration branch; base merge needs approval | Ours better |
| Cost control | No routing or budget system found (absence not proven; agent profiles #22573 open) | Dispatch rules, triage (shadow), allowlist, context caps | Ours better |
| Security | Skip-permission flags pre-applied; loopback token in agent env is forgeable (inferred) | Config trust boundary, tool guards; fail-open, "not a sandbox" | Ours better on config; both unsandboxed |
| Maturity | 467 contributors, 371 releases in 7 months, MIT; experimental orchestration | One user, heavy config, triage untuned, async deferred | Orca more mature; churn risk |

## What to change, in priority order

Status 2026-10-26: item 1 is built for runs inside Herdr (orch creates the ship worktree with `herdr worktree create`, links only `.env` unless the checkout is on main or master, and `orch close` removes a clean, merged worktree and never forces); the sections above describe the setup as researched, before that change. Messaging also gained a once-per-message Stop-hook mention, a watcher re-ring after `unread_minutes`, and session epochs that make `orch report` refuse a replaced session. Items 2, 3 and 5 to 7 are not built. Item 3 needs a different design: a `PreToolUse` timestamp only marks the start of a call, so it cannot cover a long test run; reading the transcript for an in-flight tool call can.

| # | Change | Why | Cost and risk |
|---|---|---|---|
| 1 | Make `orch` create and remove worktrees: collision check on branch, path and PR, create from the task base SHA, safe `git branch -d`, dirty check, refuse on unmerged work | Removes the `become --off` dance and model-dependent hygiene; also fixes stale worktrees | Moderate Go work; must fit the lead's expected path; preserves the "never force without asking" rule |
| 2 | Detect Claude limits and permission prompts automatically from Claude's own signals (statusLine rate-limit data, `PermissionRequest` and `StopFailure` hooks) and feed `orch health` and `ui-blocked` | Closes our biggest manual gap; Orca proves the signals exist | Unverified on our Claude version; Orca gates installs by `claude --version`; keep manual override |
| 3 | Add a last-tool-activity timestamp from the existing `orch hook pretool` as a third liveness signal beside Herdr and the fingerprint | Removes the long-test false `stalled`; cheap | Hook latency (Orca measured p50 166 ms on heavier hooks); keep the write tiny and fail open |
| 4 | Repo-config `setup` script and a literal `.worktreeinclude`-style env carry-over, run in the new worktree before the lead starts | Needed once `orch` owns worktrees; avoids leads rediscovering env steps | Small; repo files must not set launch-affecting keys, per our trust rule |
| 5 | Push a phone or OS notification only for `needs-decision` and `ui-blocked`, with no message body | The one human signal that matters when away; users ask Orca for the same split | Needs a channel choice; avoid previews for privacy |
| 6 | Confirm doorbell delivery (turn actually started) and retry once | Orca's worst bugs are unsubmitted prompts; we have the same channel risk | Low; Herdr status transition may be enough |
| 7 | Defer: optional best-of-N "race" for hard scout or design tasks | Orca's headline pattern; useful where several designs are plausible | Token cost multiplies (98% of overnight spend was leads); only on user request |

Avoid copying Orca's topic pub/sub, nested workers, group addresses and screen-scraping rules with live-downloaded updates, because they are the source of its open reliability issues and conflict with our simpler disjoint-ownership model. Also avoid pre-applied skip-permission flags, a loopback hook server with a token in agent env, and writing hooks into the user's global `settings.json` unscoped ([#24873](https://github.com/stablyai/orca/issues/24873)). Building our own GUI or mobile app is out of proportion to the benefit; the notification in #5 gets most of the value.

## Conclusion

The sharpest insight is that Orca and `orch` sit on opposite sides of the trust question. Orca trusts hooks and heuristics to tell it what agents are doing and leaves the integration decision to the human; we trust no one's "done" and verify before merging, but we leave the mechanical parts (worktrees, limits, liveness) to prompts and manual commands. Closing those mechanical gaps costs little and keeps our actual differentiator intact.

Treat the numbers and the comparison with care. Orca's 106.9k stars grew about 4x in under three months and the origin is unverified, so do not read it as a quality signal. I found no independent hands-on test of Orca orchestration against anything, and no usage data. Our side comes from local reading and memory notes that were 3-4 days old; one conflict is known, since a plan note kept `--ctx-shell` default `open` while `gate.md` and `model-roles.md` now say `ctx-only`, so check the code before relying on either. Orca's daemon, mobile relay internals, orcad install flow and per-agent hook mappings were not fully read, and Orca's product moves roughly daily, so re-check anything here before building on it.
